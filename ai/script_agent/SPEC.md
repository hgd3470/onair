## 로컬 실행 모델 · 2026-11-13

기본 생성기 provider는 `gemini`, 모델은 `gemini-4-hydrogen / medium`, pipeline.mode는 `batch`다. 큐의 단계별 다건 배치뿐 아니라 단일 generate·외부 revise·preflight의 Gemini 요청도 배치로 보낸다. OpenAI 검토와 수정 예산은 유지한다. 배치 전송은 Gemini API 키를 사용하며 Vertex 실시간 인증과 구분한다. 이번 변경은 모의 HTTP·API 없는 회귀로 검증하고 실제 배치 실행은 하지 않았다.

## 기사 재구성·언론사 인용·팀 저작권 · 2026-11-13

기본 프롬프트 v27은 기사 전문을 검증 자료로 보존하고, 대본은 검증 내용을 독립적인 문장과 구성으로 새로 작성하도록 한다. 근거 기사·사실 카드·claims가 연결된 “○○일보에 따르면” 인용은 허용한다. 의견은 기존 승인 목록·귀속·짧은 직접/간접 인용 규칙을 따른다. 아래 과거의 일괄 매체명 금지보다 이 계약이 우선한다.

이슈 수집기 대본은 실시간·배치·외부 수정 모두 최상위 license=All rights reserved, rights_notes의 © 틈(TEUM) 팀 표시를 사용한다. 원기사·입력 라이선스·원문과 검토/게시 상태는 유지한다. 독립 사실 자료는 같은 팀 권리 유보 조건을 지원하고 과거 CC0 입력은 재현용으로 읽는다. 과거 CC0 공개 선언은 새 출력에 적용하지 않는다. v5/v6 모두 실제 인용한 매체를 attribution에 재계산하며, 명시적 publish-license 실행에서도 유지한다. 변경된 프롬프트에는 새 실행 목적지를 사용한다.

# 실행·인계 계약 v1.0.0

## 원문 인계 v6의 선택적 언론 의견 인용 (v26)

기본은 사실만 전달하며 인용 0개는 결함이 아니다. 인명은 유지하며 긴 직함은 줄일 수 있고 동일 의견의 바로 이어지는 두 문장은 귀속을 공유한다. 발언 동사 목록 대신 의미 검토로 의견의 확실성을 확인한다. 근거가 연결된 인용은 다른 검사에 실패해도 일반 매체명 삭제 지시와 중복되지 않는다. 실제 사용한 매체만 attribution에 남긴다. 내용 있는 귀속 전망을 단순 출처 안내로 거부하거나 앞선 제안을 문체 취향으로 번복하지 않는다.

`issue_collector`의 새 v6 Markdown은 검증 사실과 별도 `의견 인용 목록`을 제공한다. 기본 프롬프트 v27은 v5/v6의 근거 있는 사실 보도 귀속을 허용하며, v6에는 선택적 의견 인용 정책도 적용한다. 승인 의견은 선택적으로 최대 두 문장, 언론사·실제 발언 주체·불확실성을 보존해 전달한다. 직접 인용은 원문 그대로 `quotation`, 간접 인용은 짧은 재서술로 `opinion` claim을 사용한다. 두 방식 모두 `kind=opinion` 카드의 quote(승인 구간 전체 또는 이를 포함한 동일 기사 연속 구간)와 연결하고 `conditions`에 독립 O번호 문자열을 넣는다.

최상위 `attribution`은 실제 연결된 인용 언론사 이름만 쉼표로 구분한다. URL·기사 제목·기관·기자는 제외하며 인용이 없으면 빈 문자열이다. 입력 메타데이터와 원출처 전체는 보존한다. 실시간·배치·외부 수정에서 자동 재계산하고 원문 변조·미승인 의견·귀속 누락·의견의 사실 분류를 검증한다. 의미·관련성·불확실성의 정확성은 모델의 원기사 대조 검토도 필요하다.

선택적 통합 원기사 검토는 `UseAssessment.policy_version=news-attribution-v2`, `basis=facts_with_optional_attributed_opinions`를 사용한다. 실제 의견이 있으면 `facts_only=false`와 `attributed_opinions=true`를 요구하고 통과 시 `rights_status=attributed_news_reviewed_not_legal_approval`로 구별한다. 의견 없는 결과는 기존 사실 검토 상태를 사용한다. 기사 권리·처리 허가·사람 승인·TTS 상태와는 별개다. 기존 v23 프롬프트와 출력은 보존하며 새 목적지에서 실행한다.


## 원문 Markdown 독립 인계 v5 / 프롬프트 v23 · 2026-11-12

`issue_collector`가 내보내는 `IC-*.md`를 변환 없이 읽는다. YAML frontmatter에는 `source_kind=user_summary`, 분류·목표 길이·`original_sources`가 있고, 본문에는 검증 사실·근거 매핑·`## 수집 원문` 아래 기사 전문이 있다. 생성기는 수집기의 Python 코드나 캐시를 불러오지 않는다. `.meta.json`은 필요하지 않다.

```bash
bash tools/run.sh validate-input /absolute/path/IC-20261111-issue-topic.md
bash tools/run.sh generate /absolute/path/IC-20261111-issue-topic.md --destination /absolute/path/new-output
```

`generate`는 단일 파일에 기존 실시간 생성·검토·수정 파이프라인을 실행한다. 원본은 그대로 두며 `sources[0].text_path`는 전달받은 파일을 가리킨다. 완료 JSON이 있으면 덮어쓰지 않고 `output_exists_use_new_destination`으로 종료한다. 미완료 로그는 기존 설정·프롬프트 일치 검사를 거쳐 재개한다. `--destination` 생략 시 기존 `output/<배치코드>/` 분류를 사용한다. `IC-`는 `_unbatched`다.

큐 방식도 지원한다. `.md`를 `input/`에 복사한 뒤 `run --mode standard` 또는 `run --mode batch`를 실행한다. 새 `IC-` 입력의 완료 사본은 생성기 자체 `archive/<입력 SHA-256>/`에 보관하므로 다른 수집기 폴더를 생성하지 않는다. 기존 `source_collector` 입력의 저장 경로는 유지한다.

분석·생성·검토·수정 요청의 `source_text`, 최종 JSON의 `sources[0].text`에는 원기사 전문을 포함한 입력 본문 전체를 저장한다. `sources[0].sha256`은 이 전체 본문 해시다. 원출처 목록은 `input_metadata.original_sources` 및 `sources[0].original_sources`에 보존한다. 외부 피드백도 JSON에 내장된 원문으로 수정·재검토하며 원본 파일 재조회가 필요하지 않다. v5 입력 인계 형식은 유지하며 선택적 인용의 출력 상태는 위 v6 계약을 따른다.

v5 원문 블록은 개수·순서·중복 기사 ID·본문 SHA-256을 검사한다. 사실 카드 `quote`가 검증 요약에만 있고 기사 본문에 없으면 `fact_quote_not_in_original_article`로 거부한다. v23 프롬프트는 원문과 검증 사실을 직접 대조하며, 기사에만 있는 미검증 사안을 추가하지 않게 한다. 기존 v2~v4 입력과 비뉴스 입력은 계속 지원한다. v22는 보존한다.

기본 입력 상한은 60,000→160,000자로 확대했다. `--max-source-chars` 명시값과 오류 계약은 유지하며 원문을 자동 절단하지 않는다. 입력·원기사 이용 조건은 미확인 상태를 보존하고 원문 전체에 CC0를 부여하지 않는다. 모델·effort·내부/외부 수정 예산은 유지한다. 기존 산출물은 자동 변경하지 않으며 새 설정·프롬프트는 새 실행 목적지에서 사용한다.

## 범위와 모델 역할

| 단계 | 구현 | 모델 |
|---|---|---|
| 파일 수신·중복·출처 보존 | 로컬 Python | 없음 |
| 유형 분류·소재/사실 카드 | `analyze` | gemini-4-hydrogen, medium |
| 유형별 초안 | `generate` | gemini-4-hydrogen, medium |
| 자체 검토·재검토 | `review` | gpt-6-luna, medium |
| 대본/사실 카드 수정 | `revise` | gemini-4-hydrogen, medium |
| 구조 검사·JSON 인계 | 로컬 Python | 없음 |

`analyze`·`generate`·`revise`는 `models.generator`, `review`는 `models.reviewer` 설정을 사용한다. 실행 모드는 `standard`(실시간 순차)와 `batch`(Gemini Batch API 비동기 고병렬) 중 선택할 수 있으며, 두 모드 모두 `config.toml`의 동일한 모델 설정을 공유한다. GPT의 피드백을 Gemini가 반영하고 GPT가 재검토한다. 외부 검수 피드백도 같은 Gemini 수정 경로를 사용한다. `generator.revision_model`에는 수정 담당 모델을, 단계별 `calls`에는 실제 모델과 effort를 기록한다. 과거 출력에 외부 피드백을 적용하면 현재 수정·검토 모델 정보를 갱신하고 이전 호출 이력은 보존한다.

모델 응답이 실패·미완료·스키마 위반이면 정상 대본으로 꾸미지 않는다. 다른 모델 fallback 없음. 최종 정제(S2-06), 외부 검색 기반 전체 사실 검증, TTS, 음원 적재, 배포는 수행하지 않는다.

## 입력 원문과 사실 카드

`source_text`는 front matter를 제외한 원문 본문이다. 원본 파일은 수집기의 output에, 검증에 사용한 원문 본문은 출력 JSON에 보존한다. 별도 sources 텍스트나 archive 백업을 만들지 않는다. UTF-8 BOM은 읽기 시 제거한다. 원문을 네트워크에서 자동 수집하지 않으며 링크만 입력된 경우의 원문 대조/권리 확인을 대신하지 않는다.

`SourceMeta`는 출처·저자·라이선스·기준일·목표 길이·제작 유형을 담는다. 런타임은 LLM에게 이용조건을 수정시키지 않는다. 명시된 CC 4.0 식별자 또는 공식 URL에 대해서만 코드가 비어 있는 표준 조건을 보완한다. 나머지 모르는 값은 null/unknown이다. 같은 원문이라도 메타데이터가 바뀌면 입력 SHA-256이 달라져 새 제작으로 구분한다. 입력 원본은 `input_metadata`에, 보완한 값은 `sources[].license`에 남긴다.

`source_kind`는 `original`(기본값) 또는 `user_summary`다. `original_sources[]`는 사용자 요약문의 원래 기사/자료별 title/source_url/author/license/attribution이며 수집 원문 스냅샷과 구분한다. 사용자 요약문의 원출처 누락 또는 원출처 조건 미확인은 `unverified`다. 모든 원출처 조건도 함께 평가하여 한 건이라도 제한/미확인이면 보류한다.

## 낭독 문면 규칙 (v7부터 유지)

- `script`의 한 원소는 완결된 한 문장, 공백·문장부호 포함 NFC 기준 40자 이하다. 코드는 `len(NFC(sentence))`로 센다. 공백을 빼고 43음절로 완화하지 않는다.
- 숫자·영문은 한글 읽기로 쓴다. 예: 이십 메가와트, 구 급, 에이아이, 삼 점 오 퍼센트. 코드는 NFKC 정규화 후 숫자/영문 잔존을 검사하고, 모델은 수치·단위·날짜·고유명사 의미가 유지됐는지 검토한다. 근거 원문/quote/식별자/URL은 변환하지 않는다.
- 비낭독형은 사실·조건을 추출해 새 문장과 설명 구조로 재서술한다. 코드 경고는 공백·문장부호 제외 영숫자 15자 이상에서 원문 문장과 SequenceMatcher 유사도 85% 이상 또는 원문 구간 그대로 복사를 탐지한다. 유사도 비교는 길이 비율 70% 이상인 원문 문장을 대상으로 하고, 부분 문자열 복사는 길이 비율과 무관하게 검사한다. 이 값은 편집 휴리스틱이며 법적 안전 기준이 아니다. 짧은 표현·의미 유사성·숫자를 한글로 바꾼 복사는 모델 대조가 추가로 필요하다. `quotation` 라벨만으로 비낭독형 복사 검사를 면제하지 않는다.
- 개별 발언·경험의 주체/대상/맥락/추정 강도를 보존한다. 의료진 개인 발언을 일반적인 의학 사실이나 효능으로 바꾸지 않는다. 분석 카드부터 이 범위를 기록하고 검토·수정에서 대조한다.

코드 검사는 모델의 pass를 revise로 바꿀 수 있다. 한도 소진 뒤 결함이 남으면 hold다. 원문낭독형 인용의 표기/길이 규칙이 원문 보존과 충돌하면 수정으로 원문을 훼손하지 않고 needs_evidence/hold로 판정한다.

`material.facts[]`:

- `id`: f1부터 이어지는 고유 식별자. 문장별 claims가 참조한다.
- `text`: 원문에서 정리한 주장. 외부 사실검증 완료라는 의미가 아니다.
- `quote`: 원문에 실제 존재하는 연속 구절. 코드가 부분 문자열 일치를 검사한다.
- `kind`: source_statement / opinion / fiction.
- `conditions`: 기간·범위·예외 등 해당 주장의 한정 조건.

수정 단계는 `{draft, material}`을 반환한다. v11 런타임은 `material=null`이면 기존 전체 카드를 그대로 유지한다. 사실 카드에 실제 변경이 필요할 때만 전체 material을 반환한다. 잘못 요약된 조건과 누락된 원문 근거를 카드에서도 고칠 수 있다. 원문 밖 인용, 기존 ID 삭제, 제작 유형·카테고리 변경은 거부한다. 강조 기호와 공백만 다른 인용은 정규화 비교에서 유일하게 대응하는 원문 구간을 찾았을 때에만 그 정확한 구간으로 복원한다. 숫자·부정어·절 번호·일반 문장부호는 제거하지 않으며 모호한 일치는 거부한다. 복원 뒤에도 정확한 부분 문자열 검사는 유지한다. 원본 모델 응답과 `*-quote-alignment.json`의 원문 위치·복원 전후를 보존한다. 최초/수정 카드와 단계별 입력·출력은 로그에 남는다. 문장 ID가 아니라 **배열 순서가 문장 번호**라 대본 수정 후 번호가 바뀔 수 있다. 외부 검수자는 검토한 `content_id`와 `version`을 함께 보관해야 한다. `revise --expected-version`으로 다른 버전의 문장 번호 피드백 적용을 막을 수 있다.

## 청취 이해 계약 (v8 → v12)

기본 프롬프트는 v22이며 모델 역할과 내부·외부 각각 최대 두 번의 수정 예산은 유지한다. 분석의 `question`은 한 가지 중심 질문, `summary`는 그 답, `details`는 필요한 용어 풀이·원문 예시·장면과 사실 ID, `outline`은 구체적인 도입→설명→근거→마무리를 담는다. 이 구성 계획은 기존 Material 필드로 표현하며 별도 모델 호출을 추가하지 않는다. 편집 기준과 검토 결과의 스키마 확장은 아래 v11 계약을 따른다.

생성·수정은 이 구성과 문장별 근거를 함께 유지한다. 가정 예시는 가정임을 말하고 원문 사실 ID로 연결한다. 사실형의 설명을 위해 원문 밖 사건·수치·감각 묘사를 만들지 않는다. 마무리의 사실 종합도 근거를 연결하며 `transition`으로 사실성 검사를 회피하지 않는다. 교훈 요청을 안전 보장·섭취 금지·투자나 운전 처방의 근거로 쓰지 않는다.

검토는 `용어 연결 부족`, `구체적 예시 부족`, `도입 장면 부족`, `핵심 요점·마무리 부족`, `성경 출처 안내 누락`, `근거 범위 초과` 중 적용되는 문제를 기존 `issues`로 반환한다. 이는 LLM의 의미 검토 기준이며 단어 검색으로 코드가 보장하는 규칙이 아니다. 원문 안에서 해결할 수 있으면 revise, 원고 완성에 필수적인 새 근거가 있어야만 해결되면 needs_evidence다. 기존 수정 루프가 이를 처리하며 한도 뒤 남은 문제는 hold다.

성경 본문은 첫 한두 문장에 성경과 확인된 책·장/절을 밝힌다. 이 규칙은 일반적인 사건/질문 도입보다 우선한다. 원문낭독형은 별도 안내만 허용하며 지정 원문에 풀이·예시를 삽입하거나 마지막에 해설을 덧붙이지 않는다. C21이라는 분류만으로 성경 장절을 생성하지 않는다.

v9는 실제 첫 질문과 마지막 답을 비교한 근거를 검토의 strengths 또는 issues에 남긴다. 소재 카드의 복수 주제로 대본의 주제 이탈을 정당화하지 않는다. quote는 원문 기호·공백·절 번호를 보존한 짧은 연속 구절로 선택하며 기존 유효 인용을 수정 단계에서 정돈하지 않는다. 원문 일치 코드 검사는 완화하지 않는다.

v10은 범주와 낯선 이름의 관계를 같은 문장 또는 명시적 연결어로 밝히도록 예시를 추가했다. 첫 질문에 범주만 등장하고 뒤에 이름·수치가 나오는 것은 충분한 풀이로 보지 않는다. 안전성 미확인은 연구와 평가 대상을 한정한다.

프롬프트 변경만으로 기존 출력·사람 승인 상태를 바꾸지 않는다. 실제 비교 생성은 별도 배치에 기록하며 이전 수정 이력과 혼합하지 않는다. 검토 화면의 코멘트 JSON은 맥락 자료로 읽고 CLI 수정 입력으로 자동 변환하지 않는다.

### v11 편집 요구사항·실패 진단

`Pipeline.run(..., editorial_brief=[...])`와 카테고리 배치의 `--editorial-briefs`는 명시적인 전체 원고 편집 기준을 받는다. 카테고리 배치는 선택 목록 밖 키를 거부한다. 요구사항은 최대 32개, 각각 4,000자, 합계 20,000자이며 공백만 있는 항목은 거부한다. 새 원고의 문장 번호를 요구사항 번호로 혼동하지 않는다.

요구사항이 있으면 검토 출력은 `{editorial_checks, review}`다. 상위 체크의 `requirement`는 1부터 시작하는 편집 요구 번호, `satisfied`는 충족 여부, `evidence`는 현재 대본 문장에 대한 근거다. 내부 review의 체크는 사용하지 않고 상위 체크를 최종 ReviewRecord에 결합한다. 모든 요구 번호가 정확히 한 번 존재해야 하며 false 또는 누락/중복/잘못된 번호는 기존 수정 루프로 연결한다. 수정 한도 뒤 남으면 hold다. 외부 피드백 수정에서도 원래 editorial_brief를 유지한다.

`editorial_brief`와 `self_review[].editorial_checks`는 기본 빈 배열이므로 과거 출력도 읽는다. 기존 엄격한 스키마를 사용하는 소비자는 새 handoff schema를 적용해야 한다. 일반 피드백 없는 실행은 기존 Review 흐름이다. 새 요구사항과 실제 사람 코멘트의 출처·범위는 배치 기록에서 구분한다.

ProviderError에는 Gemini 종료 사유 enum과 허용된 정수 토큰 수만 남기고, `*-error-<id>.json`은 재시도해도 덮어쓰지 않는다. 단계 응답 미완료는 성공/품질 통과로 처리하지 않는다. MAX_TOKENS 실증 뒤 생성 출력 상한을 32,000으로 변경했으며 모델·effort·수정 횟수는 유지한다. 자동 차단 우회·연결 오류 재시도·모델 fallback은 없다.

## 출력 JSON

정식 JSON Schema: `schema/handoff.schema.json`.

| 필드 | 계약 |
|---|---|
| schema_version | 현재 1.0.0 |
| content_id | S2- + 입력 SHA-256 앞 16자리 |
| created_at | Asia/Seoul 시간대 ISO 8601 |
| version | 1.0.N, N은 실제 수정 횟수 |
| category / format / production_type | 관심사 / 청취 형식 / 제작 유형 |
| target_sec | 목표 시간, 실측 아님 |
| script | 한 원소에 한 문장인 문자열 배열, 번호는 1부터 |
| claims | 문장별 kind와 fact_ids; 모든 문장 정확히 1항목 |
| sources | 원문 본문(text), 상대 text_path, SHA-256, 저자·이용조건·기준일 |
| material | 유형 판단·소재 카드·고유 사실 ID·원문 인용·조건 |
| adaptation_note | from_source / new, 원문 활용과 새 창작 구분 |
| generator | 생성/검토/수정 모델, effort, 프롬프트 버전, 수정 횟수, 실제 호출 기록 |
| self_review | 수정본별 판정·문장 피드백·보조 점수 |
| status | ready_for_downstream_review 또는 hold |
| rights_status | restricted / unverified / metadata_supplied_not_legal_approval |
| rights_notes | 자동 보완 내역·미확인 필드·충돌·제한 사유; 기본 빈 배열 |
| duration | 문자수 기반 추정치와 계산법, measured_sec=null |
| input_metadata | 수신한 출처/설정 메타데이터; 모델 생성값 아님 |
| fixture | 자체 작성 시험 자료이면 true |
| downstream_approval / tts_checked | pending / false |

상위 `license`는 서버 기존 문자열 필드와 맞춘 요약이며 상세 구조는 `sources[].license`에 둔다. `kind`, `version`, `commercial`, `modify`, `share_alike`, `url`, `evidence`를 보존한다. CC BY-SA 각색물은 라이선스·변경 표시와 동일조건 요구가 출력에 그대로 남는다.

CC 4.0의 BY/BY-SA/BY-NC/BY-ND/BY-NC-SA/BY-NC-ND만 자동 보완한다. 식별된 프로필과 명시적 필드가 충돌하면 값을 덮어쓰지 않고 보류한다. `modify=false`는 이 파이프라인의 변경 대본 배포 제한 표현이다. 원문에 대한 실제 적용 근거인 evidence는 만들지 않는다. 저자·출처가 제공된 경우 생성하는 attribution도 표시 초안이며 추가 표시 사항은 수집 담당자가 제공한다. 근거: [CC BY](https://creativecommons.org/licenses/by/4.0/), [BY-SA](https://creativecommons.org/licenses/by-sa/4.0/), [BY-NC](https://creativecommons.org/licenses/by-nc/4.0/), [BY-ND](https://creativecommons.org/licenses/by-nd/4.0/), [BY-NC-SA](https://creativecommons.org/licenses/by-nc-sa/4.0/), [BY-NC-ND](https://creativecommons.org/licenses/by-nc-nd/4.0/).

스키마 버전은 1.0.0을 유지하며 기본값이 있는 필드만 추가했다. 기존 출력은 계속 읽을 수 있다. 확인한 refine 입력 파서는 추가 키를 허용하지만 `original_sources`의 중첩 조건은 직접 검사하지 않는다. 이 생성기의 `status=hold`와 export 기본 제외 정책을 인계 경계에서 유지해야 한다.

현재 로컬 서버 `/api/v1/contents/{content_id}`는 DB에 저장된 **문자열** script를 반환한다. 이 인계 JSON을 그대로 서버 요청 DTO로 쓸 수 있다는 의미가 아니다. 적재 경계에서 배열을 개행으로 연결하고 음원/승인 등 나머지 서버 요구 필드를 처리해야 한다. 서버 변경·DB migration 없음.

## 수정 및 보류

초안 revision=0 → 검토. 문제가 없으면 종료한다. 수정 필요 시 revision 1 → 재검토 → 필요시 revision 2 → 재검토 후 종료한다. `needs_evidence`는 자료 확보 없이 더 쓰지 않고 보류한다. 이 횟수는 생성기 내부 수정만 센다. 외부 피드백 수정은 `generator.feedback_revision`으로 분리한다. 이 필드는 0 이상 정수만 허용하고 null·문자열·소수·불리언은 거부한다. 저장 값의 상한은 없으며 수정 한도는 `apply_feedback`의 `revision_budget_exhausted`로 검사한다. 0에서 시작하며 `max_revisions` 한도를 별도로 적용한다. 외부 피드백 한 회차의 결과를 저장할 때 정확히 1씩 증가하고, 내부 `revision`은 유지한다. 회차 내 자체 검토에 따른 후속 수정은 외부 회차를 추가로 소비하지 않는다. 각 회차는 지역 수정 카운터 0부터 시작해 `max_revisions`회(최초 피드백 반영 포함)까지만 수정한다. 실패로 결과를 저장하지 못하면 출력과 외부 카운터를 보존한다. 새 실시간/배치 출력에는 항상 키를 쓰고, 키가 없는 기존 JSON은 0으로 읽는다. 기존 산출물을 일괄 변경하거나 과거 외부 수정 횟수를 추정하지 않는다. 외부 검토 이력에는 내부 `revision`, 해당 회차의 `feedback_revision`, 회차 내 실제 수정 횟수 `feedback_round_revision`을 함께 기록한다. 자체 검토 문제가 한도 뒤에도 남으면 hold 상태를 유지한다.

외부 피드백은 `[{'문장 번호', '문제', '이유', '수정 방향'}]` 또는 영문 `[{'sentence','problem','reason','direction'}]`로 받는다. 0은 전체 대본이다. 범위를 벗어난 문장 번호와 빈 배열은 거부한다. 이전 출력은 로그의 before.json에 보존한다.

외부 입력의 `scope=script`는 번호가 null/생략/0일 때 전체 지적으로 처리하고 내부 Issue의 sentence는 0이다. scope가 없는 기존 형식의 명시적 null도 0으로 변환한다. scope 없이 번호까지 누락되면 오류다. `scope=sentence`는 양의 정수를 요구한다. script에 양의 번호를 함께 지정하면 `feedback_scope_conflict`, 알 수 없는 scope는 `invalid_feedback_scope`, 음수·문자열·소수·불리언 및 문장 수 초과는 `invalid_feedback_sentence`다. 별칭은 변환 전에 대조하므로 null과 0도 서로 충돌한다.

CLI는 변환 항목의 순서(1부터), scope 또는 legacy, 원래 번호 필드와 변환값을 `feedback-normalizations.json`에 기록한다. 원본 파일은 수정하지 않으며 기존 버전 확인·수정 예산은 유지한다. 버전별 수정 프롬프트 뒤에 공통 `prompts/feedback-scope.txt`를 붙이고 전체 결합문의 해시를 기록한다. 기존 체크포인트의 프롬프트와 달라지면 기존 보호 규칙에 따라 재사용을 거부한다.

`feature/refine-v1.0` 커밋 `54a9d2e`의 README와 `write_batch_reports` 출력을 확인했다. `revise.jsonl` 각 행의 `{script_id, round, decision, items}`에서 content_id와 일치하는 한 행의 items를 읽는다. 문장 키 `sentence/sent`, 방향 키 `direction/fix`는 같은 값이어야 한다. stage/category 등 검수 전용 메타데이터는 수정 Issue에서 제외한다. 다른 대본·중복 행은 적용하지 않는다. `decision=revise`만 허용하며 human_review/reject/pass 계열은 자동 수정하지 않는다. JSONL에는 version이 없으므로 CLI에서 `--expected-version`이 필수다. 외부 round는 참고값이며 외부 수정 횟수는 기존 generator.feedback_revision에서 이어간다.

아래는 자체 검토에서 pass이어도 보류할 수 있다.

- 이용 조건 미확인 또는 상업 이용/변경 불가.
- 원문에 없는 인용·연결할 수 없는 사실 ID·원문낭독 불일치.
- 실제 원고 작성을 막는 근거 부족.

TTS 미실행, 독립 검수 대기, 원문 범위 밖의 별도 주제는 그 자체로 원고 결함이 아니다. 실제 음성 길이·발음·청취 재미는 이 시스템에서 검증 완료로 표시하지 않는다.

## 파일 처리와 재실행

프로젝트당 단일 큐 잠금. 입력 파일과 sidecar를 processing의 UUID 작업 폴더로 claim하고 작업 원장을 기록한다. 출력 JSON은 임시 파일 fsync 후 replace로 게시한다. 출력 완료 후 수집기 원본을 확인·등록하고 작업 폴더의 임시 원문을 제거한다. 상태 파일만 state/completed로 이동한다. 오류는 failed에 격리한다. 401/403/429는 배치를 중단한다.

중단된 processing 작업은 다음 실행에서 다시 읽는다. 같은 단계의 프롬프트·설정·입력과 저장된 응답이 모두 일치하면 응답을 재사용한다. 일치하지 않으면 새 목적지/새 제작으로 처리해야 하며 이전 로그를 덮어써 이어가지 않는다. 네트워크 오류 직전 API가 과금됐는지는 알 수 없다.

현재는 단일 호스트 파일시스템 기반 프로토타입이다. 다중 서버 큐, 웹 UI, 스케줄러 서비스 설치는 포함하지 않는다. `watch` 프로세스가 중단되면 새 입력 자동 처리는 멈추며 재실행으로 복구한다.

## 실행 설정과 비밀키

프로젝트 루트는 `config.toml`, `prompts/`, `schema/`가 있는 `ai/script_agent/`다.
CLI는 현재 작업 디렉터리를 기본 루트로 쓰며 `--root`로 명시할 수 있다.
`bash tools/run.sh`는 호출 위치에 관계없이 스크립트가 속한 프로젝트를 루트로 선택한다.

실행 코드는 기본적으로 `<root>/.env`의 `openai_api_key`, `gemini_api_key`를 읽는다.
`--env-file`은 명시적 경로 재정의이며, 상위 폴더의 `.env`를 자동 탐색하지 않는다.
기존 환경변수(소문자 키, 대문자 키 순)가 파일 값보다 우선한다.
`.env`는 사용자가 직접 배치하고 Git·배포 ZIP에서 제외한다. 키 내용을 로그에 남기지 않는다.

## Batch 모드 실패·재개 계약 (2026-11-09)

- 새 배치는 작업별 `logs/<content_id>/batch-contract.json`에 설정·전체 프롬프트·스키마를 저장한다. 재개 시 계약과 단계별 요청을 비교하며, 다르거나 기존 로그에 계약이 없으면 `checkpoint_config_changed_use_new_destination`으로 해당 작업을 실패 처리한다. 이전 로그를 삭제하거나 계약 파일을 덧붙여 우회하지 않는다. 기존 출력·복원 기록은 그대로 보존하고 새 제작은 별도 실행 루트를 사용한다.
- 분석→생성→검토→수정→재검토의 검증된 응답을 순서대로 재사용한다. 재개 시 대본·사실 카드·검토 이력·수정 횟수를 함께 복원하며, 저장된 성공 응답은 다시 API로 요청하지 않는다. `revision-N.json`에도 당시 사실 카드를 저장한다.
- 첫/후속 수정 실패와 수정 카드 검증 실패는 해당 작업만 `failed/`로 옮긴다. 이전 수정 응답을 재사용하거나 실패 작업을 최종 출력으로 포장하지 않는다. 수정 과정의 유형·카테고리 및 기존 사실 ID 보존 검사도 적용한다.
- GPT 검토의 호출 기록과 로그 번호는 작업별로 관리한다. `generator.calls`에 Gemini와 GPT의 실제 호출 이력을 모두 포함하고, 캐시 재사용 시 중복 집계하지 않는다. 내부 수정 `revision`과 외부 수정 `feedback_revision`의 별도 예산은 유지한다.
- `logs/batch-jobs/<uuid>.json`은 공유 배치 제출 기록이다. 요청·요청 해시·작업 키·제출 상태·원격 `batch_name`·완료 응답을 저장하고, 각 단계의 `*-batch.json`이 이를 참조한다. 조회/다운로드 중 연결 오류가 나면 작업은 `processing/`에 남는다. 같은 루트와 설정으로 다시 실행하면 원격 ID를 재사용한다. 처리 limit/청크 크기/검토 워커 수를 바꿔도 제출된 작업은 재사용한다.
- 제출 POST 자체는 자동 재시도하지 않는다. 서버 수락 후 응답 유실 또는 ID 저장 직전 중단은 정확한 제출 여부를 알 수 없으므로, 재개 시 `batch_submission_unknown`으로 중단한다. 공유 기록의 `display_name`으로 공급자 측 작업을 확인하고, 일치하는 작업 ID가 확인되면 그 기록의 `batch_name`과 `state="submitted"`를 복구한 뒤 재개한다. 제출되지 않았다는 확인 없이 기록을 지우거나 `prepared`로 되돌리지 않는다. 로컬 파일과 원격 서버 사이의 원자적 제출을 보장한다는 뜻은 아니다.
- 새 계약 이전의 미완료 배치를 자동 변환하지 않는다. 완료된 기존 output은 중복 처리 대상으로 보존한다. 실제 모델 품질·사람 승인·TTS 통과는 이 재개 검증과 별개다.

### 2026-11-12 TTS 속도 보정

사용자 실측 500자/60초를 공백·문장부호 포함 NFC 글자 수로 해석한다. 기본값은 `chars_per_sec=500/60`, `character_count_mode=with_spaces`이며 문장을 공백 하나로 이어 센다. 30/60/90초의 목표는 250/500/750자다. 실시간·배치 생성과 수정의 목표 문자수, 결정적 분량 검사, 결과 `duration` 추정은 같은 기준을 사용한다. `measured_sec`는 개별 음성 실측 전에는 null이다. 모드가 없는 과거 설정은 공백 제외 계산을 유지하며 새 계산은 기존 산출물에 소급하지 않는다. 설정·시스템 프롬프트가 변경되므로 재개는 새 목적지를 사용한다.

뉴스처럼 절대 시간 범위가 필요한 제작은 `duration_min_sec`, `duration_max_sec`를 pipeline 설정에 함께 지정한다. 양수·최대 600초·하한 이하 상한 금지를 검사한다. 실시간/배치 검토에서 이 범위는 목표 분량 70~130% 허용과 별도로 적용하며, 범위를 벗어나면 수정 또는 hold다. 새 이슈 수집기 데모는 30~90초를 지정한다.


## 이슈 수집기의 사실 재서술 검토 연계 (구형 v2/v3 계약)

Handoff의 선택 필드 `use_assessment`는 원문 라이선스와 분리된 사실 재서술 편집 검토 및 기사별 조회·저장·모델 전송 판단이다. 기존 SourceMeta와 입력 해시 계약은 바꾸지 않는다. 기록 없는 기존 생성/배치의 권리 판정도 유지한다. 기록이 있으면 `use_assessment.apply_use_assessment`로 최종 내용 해시·출처 범위·문장별 검토 완료·기존 자체검토 통과 여부를 확인한다. 이슈 수집기가 기사 전문·교차 검증 기록을 대조하고 실제 GPT 검토 후 해당 기록을 발급한다. 메타데이터 표시만으로 우회할 수 없다.

통과한 사실 재서술은 원래 license가 unknown이어도 `rights_status=facts_only_reviewed_not_legal_approval`, `status=ready_for_downstream_review`가 가능하다. 수집·처리 근거가 없으면 별도 `release_status=pending_processing_review`, 유효하면 `pending_editorial_approval`이다. 내용 문제/오래된 검토는 `pending_content_review`/hold, 명시적 처리 금지 또는 기존 이용 제한은 blocked/hold다. 이 상태들은 법적 허가나 공개 승인이 아니며 downstream_approval은 pending으로 유지한다. 게시 연계자는 공개 직전 게이트를 재계산하고 처리 근거·사람 승인을 별도로 확인해야 한다.

외부 피드백으로 대본·근거·자체 검토 이력이 변경되면 이전 검토 해시가 맞지 않아 hold로 돌아간다. 기존 검토는 감사 기록으로 보존하며 수정 예산을 초기화하지 않는다. 이후 이슈 수집기의 `assess-use --demo-id ...`로 재검토한다. 이 PR은 생성기 측 인계 계약만 포함하며 이슈 수집기 실행 코드·운영 도구는 별도 작업이다. 수집기 재검토 명령은 이 PR만 설치한 환경에서는 제공하지 않는다.


## v20 뉴스 맥락 보존 및 자동 검사 (2026-11-12)

v20 도입 시점에 기본 프롬프트를 v20으로 갱신하고 v19를 보존했다. 현재 기본값은 v22다. `issue_collector`의 인계 v2는 사실 블록에 기관 귀속·사건/발표 기준일·유형을 포함한다. 이 정보는 분석부터 생성·검토·수정까지 동일한 source_text로 전달된다. 분석 카드의 text/conditions는 주체·계획 상태를 보존하고 quote는 원문 연속 구간 계약을 유지한다. SourceMeta 스키마나 기존 입력 해시 계산은 바꾸지 않았다.

`news_context.news_checks`를 기존 `validation.checks`에 연결했다. 인계 v2의 명확한 계획 동사를 완료형으로 옮긴 제목/관련 주장과 C08의 알려진 지수명 자리별 오독을 자동 수정 지적으로 만든다. 지수명은 코스닥 백오십·코스피 이백·케이알엑스 삼백으로 읽되 소수부나 식별번호를 일괄 치환하지 않는다. 복합 의미·혼합 시점은 v20 GPT 검토로 확인하며, 단순 패턴 검사만으로 모든 예정/완료 오류를 검출한다고 가정하지 않는다. 공통 검사이므로 실시간·배치·외부 피드백의 기존 수정 예산 및 한도 후 hold 계약이 적용된다. 원문낭독형 원문 보존, 권리 분리, 기존 로그 재사용 제한은 유지한다. 변경된 프롬프트/입력은 새 목적지에서 실행한다.


## v21 사건 중심 뉴스 편집 (2026-11-12)

이 단계에서는 기본 프롬프트를 v21로 변경하고 v20을 보존했다. 현재 기본값과 v4 인계 경계는 아래 v22 절을 따른다. 뉴스 인계 v3는 내부 보도 매체 목록을 낭독용 사실과 구분한다. 신문·방송·통신사 이름과 출처 안내는 제목/script에서 제외하고 원문·메타데이터·로그에서 보존한다. 실제 발표 기관·행위 주체는 유지한다. 첫 한두 문장은 사건과 검증된 주체·날짜로 시작하고 브리핑 안내/한국시간 안내를 쓰지 않는다. 합니다/했습니다/입니다/됩니다체를 유지하며 해요/죠를 섞지 않는다.

`news_context.news_style_checks`는 인계 v3의 위반을 기존 공통 checks에 반환하므로 실시간·배치·외부 수정 모두 같은 수정 예산/hold 계약을 따른다. 매체 목록에는 공식 기관을 넣지 않는다. 기관·날짜·통계명 혼동과 자연스러운 오프닝은 v21 GPT 검토에서 확인한다. 날짜·인용·입력 해시 및 권리 분리 계약은 유지한다. 구형 v2는 읽을 수 있으며 기존 결과를 소급 재작성하지 않는다. 새 프롬프트/인계 포맷은 새 실행 목적지를 사용한다.


## v22 독립 사실 소스 인계 (과거 v4 입력 호환)

현재 기본 프롬프트는 v27이며 다음은 v22 당시 계약이다. 이슈 수집기의 인계 v4는 기사 대조 후 독립적으로 작성한 사실 자료만 받는다. 기존 스키마에서 `source_id=ICF-...`, `author="이슈 수집 에이전트"`, `source_kind="original"`, `source_url=null`, `license.kind="CC0-1.0"`, `attribution=""`로 식별한다. original은 새로 작성된 입력 자료를 뜻하며 원기사를 뜻하지 않는다. 일반 user_summary의 원출처 기록 계약은 변경하지 않는다.

`fact_source.fact_metadata`와 SourceMeta/SourceSnapshot 직렬화가 이 계약에 한해 빈 `original_sources` 키를 제외한다. 원기사 목록·URL 또는 잘못된 source_kind/라이선스가 붙으면 거부한다. 실시간·배치·외부 피드백 요청과 최종 JSON에 같은 경계를 적용한다. `complete_license`는 명시된 CC0의 조건과 근거를 검사하고 attribution을 요구하거나 자동 생성하지 않는다. CC0는 입력 제공자의 보유 권리에 대한 공개 선언이며 법적 무해성이나 서비스 게시 승인이 아니다.

원기사와 처리 권한 판단은 이슈 수집기 내부에 둔다. 새 Handoff에는 원기사별 use_assessment를 넣지 않으며, 수집기의 별도 최종 원기사 대조를 거쳐 상태만 반영한다. 수집기 외부 피드백 도구는 내용이 바뀌면 이전 판단을 무효화하고 재검토를 요구한다. 대본 생성기 단독 결과를 수집기의 원기사 대조 완료로 해석하지 않는다. 기관 귀속·날짜·예정/완료·낭독 규칙과 뉴스 문체 검사는 v4에도 적용한다. 기존 v21 입력·데모·로그는 보존하며 새 계약은 새 실행 목적지를 사용한다.
