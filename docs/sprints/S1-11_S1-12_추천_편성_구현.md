# S1-11·S1-12 추천과 시간·광고 편성

기준일: 2026-11-05. 구현 기준: `feature/recommendation-core` 작업 트리.

이 문서는 S1-11 추천 본체와 S1-12 유한 시간 편성의 현행 계약이다. 과거 문서의 ‘이야기 2편마다 광고’, 종료 7분/3분 전 광고 금지, 골라 듣기의 일률적인 5개 중 최대 3개 규칙보다 우선한다. 기존 임시 편성은 `mode=legacy`에서만 유지한다. 새 세션 API·관리자 페이지·청취 DB·차량 플레이어는 만들지 않았다.

## 1. 구현 결과와 담당 경계

| 영역 | 구현 내용 |
| --- | --- |
| S1-11 | 관심사·좋아요·보관·완청·미청취·태그·선택 이력·스킵 신호를 이용한 결정적 규칙 추천, 설명 근거, 고정 기준선 |
| S1-12 | 음원 길이와 이야기 배속을 반영한 편성, 시간 상한, 선택 대분류별 이야기 시간 하한, 광고 비중 하한·상한, 광고 중복 회피, 이야기로 시작·종료, 부족 응답 |
| HTTP | 기존 `GET /api/v1/playlist`에 두 본체 연결. 기존 필수 요청과 기본 응답 필드 유지 |
| 정책 관리 | 불변 `PlaylistPolicy` 객체, 검증, JSON 파일 공급자, FastAPI 의존성 교체 지점. 요청마다 적용된 정책을 응답에 포함 |

| 앱 담당 경계 | A–E를 C코드로 확장, 재생·광고 표시·속도 적용·다음 5개 표시·현재 이야기 유지·세션/큐/복원·이벤트 전송 |

API에서 **연결된 신호**는 저장 관심사, 좋아요/취소, 보관/취소, 기존 청취 history다. **선택 이력과 스킵 타이밍은 계산 본체만 있고 HTTP 저장/조회 연결은 아직 없다.** 라우터는 빈 입력을 넘기고 `signal_status`에 `not_connected`를 반환한다. 이번 작업으로 이를 실제 수집 중이라고 해석하면 안 된다.

## 2. 추천과 골라 듣기

### 추천 모드

명시/저장 관심사에 가점을 주되 다른 주제도 추천한다. 대체 후보가 있으면 연속 5개 슬롯에서 같은 A–E 대분류를 최대 3개로 제한한다. 공급·시간 제약으로 대체 후보가 없으면 완화한다. C21은 명시 관심사에 있을 때만 후보에 들어간다.

### 골라 듣기 모드

선택한 C코드 안에서만 편성한다. A–E 전체 선택은 앱이 정본 `catalog/categories.py`의 GROUPS를 이용해 C코드로 펼쳐 요청한다. 공급 없는 코드도 조회 요청에 유효하다. 입력 C코드가 속한 대분류를 서버가 다시 계산하므로 별도 `selected_group_ids` 요청은 필요 없다.

**선택한 대분류마다 실제 편성된 이야기 시간의 최소 10%를 목표로 확보하고, 나머지를 개인화 순위로 채운다.** 유한 골라 듣기에서는 이 시간 비중 정책을 적용하고 5개 중 최대 3개 제한을 중복 적용하지 않는다. 한 대분류만 선택하면 해당 대분류 이야기만 나온다.

예: A/B를 고르고 이야기 시간이 총 1,620초라면 A와 B는 각각 최소 162초다. A/B를 50:50으로 강제하지 않는다. A/B/C/D/E를 모두 선택하면 각 10%를 확보하고 나머지 약 50%는 선호와 실제 공급에 따라 달라진다. 편 단위로 넣기 때문에 정확히 10%로 떨어지지 않아도 된다.

하한의 분모는 **광고를 뺀 실제 편성 이야기 재생 시간**이다. 요청 30분에 공급 부족으로 이야기 12분만 들어갔다면 그 12분이 기준이다. 원본 음원 시간이나 실제 완청 시간은 아니다. 2배속 이야기 120초는 이 계산에서 60초다. 세부 주제 C코드 각각에 10%를 주는 정책도 아니다.

가능하면 각 선택 대분류에서 한 편 이상을 확보한다. 한 편이 전체 이야기의 3%뿐이면 ‘한 편이 나왔으므로 충족’으로 처리하지 않는다. 시간/공급/완청 제외 때문에 충족할 수 없으면 `topic_quotas`에 실제 비중과 미달 사유를 반환한다. 선택 밖 주제나 완청 이야기를 끌어오거나 기존 이야기를 반복해 채우지 않는다.

하한은 **편성상의 노출 기회**다. 사용자가 그 이야기를 스킵했다고 자동으로 같은 주제를 계속 채워 넣어 완청을 강제하지 않는다. 다음 요청에서 이미 편성/소비한 이야기를 제외하고 누적 노출을 관리하는 것은 호출자 경계다.

## 3. 광고 비중: 기본 하한 10%, 상한 15%

이 값은 서비스 초기 정책이며 방송사의 법적 광고 상한을 그대로 적용한 것이 아니다. 검증 전 수익성·사용자 만족도를 보장하는 수치도 아니다.

```text
S = 실제 편성 이야기 재생 시간 합계 (이야기 배속 반영)
A = 실제 편성 광고 재생 시간 합계 (1배속)
T = S + A
광고 비중 = A / T
기본 목표: 0.10 <= A / T <= 0.15
```

| 전체 편성 시간 T | 하한 10% | 상한 15% |
| --- | ---: | ---: |
| 15분 | 90초 | 135초 |
| 30분 | 180초 | 270초 |
| 60분 | 360초 | 540초 |

이 표는 **그 시간만큼 실제 편성됐을 때**의 값이다. 요청 30분인데 공급 부족으로 20분만 편성했다면 20분을 분모로 계산한다. 이야기만 30분에 광고 3분을 더하면 광고 비중은 10%가 아니라 약 9.09%다. 이야기 S가 먼저 정해졌다면 최소 광고는 `S × 하한 / (1 - 하한)`이다.

광고는 편 단위로 넣는다. 10%를 맞추려고 광고를 잘라 넣지 않으며, 올림 때문에 15%를 초과하는 것도 허용하지 않는다. 이야기 180초와 광고 20초는 전체 200초의 10%로 허용된다. 이야기 80초에 광고 30초는 약 27.27%여서 거부된다.

상한은 반환되는 모든 새 편성에서 지키는 제약이고, 하한은 충족 가능한 계획을 우선 찾는 목표다. 광고가 없거나, 광고 뒤 이야기까지 넣을 수 없거나, 광고 길이 단위와 상한 때문에 하한을 맞추지 못하면 하한 미달을 명시한다. **광고를 못 넣었다고 정상 이야기를 전부 비우거나 오류로 종료하지 않는다.** 정책 파일 자체가 잘못된 경우의 503과 구분한다.

### 배치 위치

- 첫 항목과 마지막 항목은 이야기다.
- 광고는 이야기와 이야기 사이에만 넣는다. 이야기를 중간에 끊지 않는다.
- 광고끼리 연속으로 넣지 않는다. 이야기 N편이면 광고는 최대 N-1개다.
- 광고마다 뒤에 실제 이야기 한 편을 함께 확보한다. 다음 항목을 나중에 구할 수 있을 것이라고 가정하지 않는다.
- 광고 위치는 이야기 누적 시간의 균등한 지점에 가까운 서로 다른 경계로 분산한다. 콘텐츠 길이에 따라 간격은 달라진다.
- **7분 금지선은 없다. 별도의 종료 3분 전 금지선도 두지 않는다.** 남은 3분에 `광고 30초 → 마지막 이야기 150초`가 온전히 들어가면 허용한다.
- 첫 광고 전/광고 사이에 ‘무조건 5분’ 같은 별도 최소 시간을 두지 않는다. 첫 이야기와 연속 광고 금지가 기본 보호 규칙이다.

이 보장은 반환된 계획을 끝까지 재생했을 때의 보장이다. 사용자가 앱을 닫거나 마지막 이야기를 스킵하는 상황까지 통제하지 않는다. 무한 추천의 다음 5개 창마다 마지막을 이야기로 강제한다는 뜻도 아니다. 이 정책은 `recommend()`가 반환하는 유한 편성 전체를 기준으로 한다.

### 중복 광고와 개인화

**동일 편성 안에서는 서로 다른 광고 소재를 우선하고, 하한 등을 맞추기 어려울 때만 재노출한다.** 광고 소재의 구분 키는 `content_id`다. 같은 음원을 다른 ID로 중복 등록한 경우까지 동일 소재로 판별하지는 않는다.

길이가 다른 광고의 조합도 탐색한다. 재노출이 필요한 조합에서도 가능한 한 여러 소재를 사용한다. 선택한 소재를 한 차례씩 배치한 뒤 다음 순회를 배치한다. 광고 사이에는 반드시 이야기가 있다. 응답에 `unique_creatives`, `repeat_count`를 넣어 재노출량을 확인할 수 있다. 여기서 repeat_count는 ‘광고 노출 수 - 서로 다른 광고 ID 수’다.

사용자의 관심사·좋아요·스킵으로 광고를 개인화하지 않는다. 광고의 선택/순서는 길이, 비중, 슬롯 수, 소재 중복 수, ID에 따라 결정적이다. 사용자나 세션 간 광고 노출 이력은 조회하지 않으므로 같은 사용자의 다음 요청에서도 같은 광고가 나올 수 있다. 광고 스킵 정책·과금 인정 조건·브랜드별 빈도 제한은 포함하지 않는다.

## 4. 설정을 바꾸는 방법

### 순수 함수 호출

```python
from teum.playlist.policy import PlaylistPolicy
from teum.playlist.recommendation import recommend

policy = PlaylistPolicy(
    policy_id="experiment-2026-11-05",
    ad_min_ratio=0.10,
    ad_max_ratio=0.15,
    selected_group_min_ratio=0.10,
)
result = recommend(contents, minutes=30, history=history,
                   interests=["C01", "C06"], mode="pick",
                   speed=1.0, policy=policy)
```

본체는 정책 파일·DB·환경변수를 읽지 않는다. `policy`를 생략하면 위 기본값을 쓴다. `PlaylistPolicy`는 frozen dataclass라 호출 중 변경되지 않는다.

### 서버 운영 설정

`server/teum/playlist/policy.example.json`을 운영용 경로에 복사하고 아래 값을 수정한다.

```json
{
  "policy_id": "production-2026-11-05-v1",
  "ad_min_ratio": 0.10,
  "ad_max_ratio": 0.15,
  "selected_group_min_ratio": 0.10
}
```

서버 실행 환경의 `TEUM_PLAYLIST_POLICY_FILE`을 그 파일 경로로 지정한다. 환경변수가 없으면 코드 기본값이다. 설정된 파일은 **요청마다 새로 읽고 검증**하므로 파일 교체는 다음 요청부터 반영된다. 이미 응답한 큐는 바뀌지 않는다. 환경변수의 경로 자체를 변경하려면 서버 프로세스의 환경 설정을 갱신해야 한다.

운영에서는 새 파일을 별도 경로에서 검증한 뒤 같은 파일시스템에서 원자적으로 교체한다. 파일을 제자리에서 쓰다가 중간 내용이 읽히면 해당 요청은 실패할 수 있다. 예시 검증은 서버 디렉터리에서 다음처럼 수행한다.

```python
import json
from pathlib import Path
from teum.playlist.policy import PlaylistPolicy

candidate = PlaylistPolicy.from_dict(json.loads(Path("policy.next.json").read_text(encoding="utf-8")))
print(candidate.to_dict())
Path("policy.next.json").replace("policy.json")  # 실제 운영 경로에 맞춰 사용
```

| 설정 | 기본값 | 검증 |
| --- | ---: | --- |
| policy_id | default-v1 | 비어 있지 않은 문자열. 운영자가 개정마다 다른 값 부여 |
| ad_min_ratio | 0.10 | 0 이상, ad_max_ratio 이하 |
| ad_max_ratio | 0.15 | ad_min_ratio 이상, 1 미만 |
| selected_group_min_ratio | 0.10 | 0 이상 0.20 이하. 5대분류 합계 하한이 100%를 넘지 않도록 제한 |

NaN/Infinity, 숫자 문자열, bool, 알 수 없는 필드, JSON의 중복 키를 거부한다. 일부 필드만 넣으면 나머지는 기본값을 사용한다. 배포 파일에는 전체 필드를 명시하는 것을 권장한다. 광고를 끄려면 **하한과 상한을 모두 0**으로 둔다. 대분류 하한 0은 시간 비중 하한을 끈다. 선택 주제 필터는 그대로다.

파일 누락·읽기 오류·잘못된 JSON·검증 실패 시 새 추천 API는 `503 {"detail":"playlist policy unavailable"}`를 반환한다. 조용히 이전 값이나 기본 광고 비중으로 바꾸지 않는다. `mode=legacy`는 새 정책 공급자를 호출하지 않아 이 오류의 영향을 받지 않는다. 파일 경로와 내부 오류 내용은 응답에 노출하지 않는다.

### 나중에 관리자 페이지를 연결할 지점

`policy_provider.get_policy_provider()`가 `() -> PlaylistPolicy` 읽기 함수를 제공한다. 현재 함수는 JSON을 읽는다. 향후 관리자 담당은 인증된 관리자 API/DB에서 정책을 저장하고, 이 공급자를 ‘활성 정책을 읽어 검증된 객체로 반환’하는 함수로 교체하면 된다. 추천 점수 계산과 편성 알고리즘을 수정할 필요가 없다.

한 요청에는 한 번 읽은 정책 스냅샷만 사용한다. 응답의 `policy`에 ID와 전체 값이 포함되어 재현에 활용할 수 있다. 관리자 쓰기 API·접근 권한·변경 이력·승인·다중 서버 동기화·캐시는 이번에 구현하지 않았다. 일반 사용자가 쿼리로 광고 비중을 낮추는 입력도 추가하지 않았다. 공급자 교체 테스트는 FastAPI dependency override로 검증했다.

## 5. 추천 점수와 신호

분류 정본은 PR #10에서 가져온 `server/teum/catalog/categories.py`의 C01–C21/GROUPS다. `playlist/topics.py`는 정본을 읽는 뷰다. DB 이관을 자동 실행하지 않는다.

점수 구성:

```text
4 × 명시 관심사 여부
+ 2 × 카테고리 반응 선호
+ 태그 반응 선호
+ 0.5 × 미청취 여부
+ 0.3 × 해당 이야기 보관 여부
+ 0.3 × 과거 대분류 선택 선호
- 해당 이야기의 스킵 감점
```

반응 증거는 좋아요 0.7, 보관 0.3, 완청 0.2를 합해 콘텐츠당 최대 1이다. 카테고리/태그별 합을 `3 + 증거 콘텐츠 수`로 나눠 적은 증거의 과도한 영향을 줄인다. 태그는 정규화한 문자열 일치다. 본문 임베딩/학습 모델이 아니다. 완청한 콘텐츠는 선호 증거로 쓰되 자동 추천 후보에서는 제외한다. 취소한 좋아요/보관은 양의 증거에서 제거하며 싫어요로 취급하지 않는다.

동점이면 관리번호와 ID로 결정한다. 첫 사용자에게 개인화 증거가 없으면 순서가 고정될 수 있다. `baseline=True`는 고정 관리번호 기준선이며 개인화 점수 순서/다양성/골라 듣기 비중 예약을 적용하지 않는다. 광고·시간의 안전 제약은 동일하게 적용한다. 기준선은 함수용이며 새 HTTP 쿼리가 아니다.

선택 이력은 첫 실제 재생이 시작된 `TopicSelection(selection_id, selected_at, group_ids, playback_started)`만 사용한다. 최근 30일, 14일 반감기, UTC 하루 기여 합 1 상한, 중복 제거를 적용한다. 단순 화면 클릭/미재생 선택은 반영하지 않는다.

스킵은 사용자 다음 동작임을 확인할 수 있는 정상 재생 로그에 한해 해당 콘텐츠만 감점한다. 실제 들은 시간이 10초 이하이면서 비율 20% 미만이면 0.5, 그 외 80% 미만이면 0.2를 기본 감점으로 삼아 14일 반감기를 적용한다. 같은 카테고리의 다른 콘텐츠에는 감점을 전파하지 않는다. 탐색/중단/불완전 로그·지원하지 않는 버전은 보수적으로 제외한다. 좋아요/보관/완청 콘텐츠도 감점하지 않는다.

스킵 본체는 정규화된 event_id, content_id, playback_id, seq, type, position_sec, playback_rate, client_ts(Unix 초), content_version, skip_reason=user_next를 입력받는다. 이는 기존 HTTP 이벤트 스키마에 필드를 추가했다는 뜻이 아니다. 공식 completed는 listening의 결과를 그대로 받아 사용하며 추천이 ‘마지막 위치 80%’로 재판정하지 않는다.

## 6. 시간 편성과 제약의 우선순위

시간은 소수 첫째 자리(0.1초) 단위로 보수적으로 계산한다. 이야기의 `원본 길이 / speed`, 광고 원본 길이를 각각 올림하고, 요청 예산은 내림한다. 각 반환 항목의 시작/길이를 합산하면 전체 편성 시간이 된다. 반올림으로 예산을 넘기지 않는다. 실제 MP3 재생 지연·버퍼링 시간은 모델링하지 않는다.

**광고는 1배속**으로 계산하고 항목에 `playback_rate=1.0`을 반환한다. 이야기는 요청 speed다. `duration_sec`은 이 속도가 적용된 예상 재생 시간이며 원본 길이 필드가 아니다. 앱은 이 필드를 다시 speed로 나누지 않아야 한다. 실제 플레이어에서 항목별 속도를 적용하는 작업은 앱 담당이며, 이번에 플레이어를 수정하지 않았다.

계획은 다음 순서로 고른다.

1. 공개/가용 카탈로그, 선택 범위, 완청 제외, 전체 시간 상한, 광고 상한, 첫·마지막 이야기, 광고 연속 금지는 항상 지킨다.
2. 선택한 대분류의 등장 수를 우선 확보하고, 대분류 시간 하한을 만족하는 계획을 우선한다.
3. 그 안에서 광고 하한을 만족하는 계획을 우선한다.
4. 광고 재노출 횟수를 줄인다.
5. 위 조건이 같으면 이야기 편성 시간을 늘린다. 이어 서로 다른 광고 소재 수가 많은 계획, 광고 시간이 짧은 계획 순으로 고른다.

따라서 광고 하한을 맞추려고 선택 대분류를 없애지 않는다. 광고 하한과 대분류 하한 모두 구조적으로 불가능할 수 있으며, 그 경우 미달을 보고한다. 반복을 줄이는 계획이 우선이므로 잔여 시간이 조금 더 남을 수도 있다. 광고 개인화 점수나 광고 수익 단가는 이 우선순위에 없다.

구현은 광고 길이의 도달 가능한 합을 동적 계획법으로 찾고, 서로 다른 소재 조합과 필요한 재노출을 조합한다. 광고 예산별로 희소한 선택 대분류를 먼저 예약하고 나머지를 선호 순으로 채운다. 최소 비중 예약에는 점수 우선/짧은 편 우선 두 후보를 비교한다. 추천 모드에는 기존 다양성 규칙을 적용한다.

이 방식은 **전역 최적해를 증명하는 최적화기가 아니다.** 광고 예산 후보가 많으면 최대 256개로 제한하고 `planning.ad_search_limited=true`를 반환한다. 희소/복잡한 길이 조합에서는 가능한 해를 놓칠 수 있다. `no_compliant_ad_plan_found`, `quota_plan_not_found`는 ‘현재 탐색에서 찾지 못함’이며 수학적으로 불가능하다는 증명이 아니다. 속도를 위해 제한을 둔 결정적 탐색이고, 평가 결과에 따라 개선할 수 있다.

요청 시간을 반드시 가득 채우려고 이야기를 자르거나 반복하지 않는다. 현재 재생 중인 항목의 유지, ETA 변경에 따른 큐 교체, 배속 변경 후 재계산, 세션 중복 제외는 호출자가 현재 상태와 제외 대상을 결정한 후 본체를 호출하는 경계다. 이번에는 서버가 재생 상태를 소유하는 세션 API를 추가하지 않았다.

## 7. API와 응답 읽기

```http
GET /api/v1/playlist?user_id=u_example&minutes=30
GET /api/v1/playlist?user_id=u_example&minutes=30&mode=pick&interests=C01,C02,C03,C04,C05,C06,C07,C08,C09,C10,C11,C12&speed=1.5
GET /api/v1/playlist?user_id=u_example&minutes=30&mode=legacy
```

- 기존 필수 user_id/minutes, 선택 interests/speed 계약을 유지한다. mode 생략은 recommend다.
- interests 생략/빈 문자열/공백·쉼표만 있으면 `listening.interests(user_id)`를 조회한다. 쿼리가 있으면 쿼리가 우선이며 저장값을 바꾸지 않는다. legacy에도 같은 fallback을 적용한다.
- minutes는 유한한 (0, 600], speed는 유한한 (0, 3]이다. pick에서 유효 관심사가 없으면 422다.
- 현재 카탈로그의 기존 영어 category는 호환 허용하지만 A–E 비중에는 임의 매핑하지 않는다. 실제 대분류 하한을 사용하려면 C코드 카탈로그/요청을 사용한다.
- 새 추천은 실제 음원 파일이 있는 공개 후보만 사용한다. 정책 파일로 비공개 음원을 공개하거나 광고를 자동 등록하지 않는다.
- 기존 items, total_sec, budget_sec, leftover_sec, rule을 유지하고 아래 정보를 추가한다. 기본 순서/광고 편성은 의도적으로 변경된다. legacy는 예전 광고 규칙까지 보존하므로 새 안전 정책이 적용되지 않는다.

| 응답 필드 | 의미 |
| --- | --- |
| algorithm_version | 순위 알고리즘 버전, 현재 r1-group-cap-direct-skip-v5 |
| planner_version | 새 편성 버전 s1-12-quota-ads-v1 |
| policy | 실제 적용한 정책 ID와 전체 값 |
| advertising.planned_sec / story_sec | 광고/이야기 예상 재생 시간 |
| advertising.actual_ratio | 광고 / 전체 편성 시간 |
| advertising.required_min_sec / allowed_max_sec | 실제 편성 총시간 기준 하한/상한 초 |
| advertising.minimum_met / reason | 하한 충족 여부와 미달 사유 |
| advertising.unique_creatives / repeat_count | 소재 수/재노출 횟수 |
| topic_quotas[] | 골라 듣기의 group_id, planned_sec, actual_ratio, required_sec, minimum_met, reason |
| packing / shortage | 시간 단위로 못 넣은 잔여와 후보 부족 구분. 잔여가 있다고 모두 오류가 아님 |
| planning | 탐색 방식과 광고 예산 후보 제한 여부/개수 |
| signal_status | 기존 반응 연결, 선택 이력/스킵 타이밍 미연결 상태 |
| items[].playback_rate | 이야기 speed 또는 광고 1.0 |

광고 미달 사유: `no_story_planned`, `no_eligible_ads`, `no_compliant_ad_plan_found`. 대분류 미달 사유: `no_fitting_group_content`(후보 없음/예산보다 큼), `quota_plan_not_found`(후보는 있으나 현 탐색의 편성에서 하한 미달). 미달은 HTTP 200의 정상 결과로 반환한다.

주제 쿼터가 필요 없는 recommend에서는 `topic_quotas=[]`다. 광고 없는 카탈로그는 이야기를 정상 반환하며 광고 하한만 미달이다. 완료/공급 부족 등의 `shortage.code`와 광고/주제 미달은 별도 정보를 봐야 한다.

## 8. 다음 5개 UI와 연결

이 API는 다음 5개만 반환하는 세션 API가 아니라 유한 시간의 전체 편성을 반환한다. 앱은 전체 큐를 보관하고 현재 재생 항목을 제외한 다음 최대 5개를 표시하면 된다. 광고도 큐의 한 슬롯으로 취급한다. 5개 미만만 남으면 있는 만큼 표시하고 가짜 항목/중복으로 채우지 않는다.

`queue_candidates.next_candidates()`는 기존 계약대로 독립적인 **이야기 후보 보충 함수**다. 광고를 넣지 않고 전체 세션의 광고/주제 누적 하한도 관리하지 않는다. finite pick의 새 하한을 유지하려면 편성 결과를 소비하거나 호출자가 전체 상태를 가지고 재편성해야 한다. 이 함수만 반복 호출해서 광고 10%가 자동 유지된다고 해석하면 안 된다.

## 10. 실행 검증과 관측 결과

최종 전체 서버 테스트 **134개 통과**. 기존 Starlette/httpx 사용 중단 예정 경고 1건이 있으며 테스트 실패는 없다. 테스트는 서버 디렉터리에서 `../.venv/Scripts/python.exe -m pytest -q tests`로 실행한다. 실제 FastAPI·임시 SQLite를 사용하는 기존 API 회귀와, 정책 파일/공급자 교체, 광고 상·하한, 종료 직전 광고, 한 편/빈 공급, 비율 단위 불일치, 배속, 대분류 부족, 광고 종류 우선/재노출, 입력 불변성, 고정 난수 카탈로그 50개를 검증한다. 테스트 카탈로그의 ID3 파일은 HTTP 가용성 검증용이며 실제 MP3 청취 테스트가 아니다.

기존 37편 추천 시나리오 16개를 통과했다. 추가로 같은 37편과 정적 데모 광고 4편의 메타데이터로 다음 8개 시나리오를 실행해 시간 상한·마지막 이야기·광고 연속 금지·이야기 중복 금지·광고 상한 등을 확인했다.

| 시나리오 | 전체 편성 초 | 광고 초 | 광고 비중 | 서로 다른 광고 / 재노출 | 주제 하한 |
| --- | ---: | ---: | ---: | --- | --- |

대본의 길이는 `target_sec`라는 **제작 목표값**이다. 광고 길이는 데모 `public/data/ads.json`의 12.722~14.759초 값을 읽어 0.1초 단위로 보수적으로 올림했다. 과거 음원의 길이를 새 원고에 적용한 것이 아니다. 모든 URI는 mock이고 콘텐츠 공개/DB 등록을 하지 않았다. 이 표는 추천 만족도나 실제 광고 매출의 검증이 아니다.

현재 광고가 짧고 4종뿐이라 기본 하한을 충족하면 재노출이 적지 않다. 알고리즘이 미달을 숨기거나 광고 공급이 충분하다고 가정하지 않는다. 실제 운영 전 소재 수 확대, 허용 재노출량, 실제 광고 재생/완료 지표를 검토할 수 있다. 이번 구현은 사용자 합의대로 ‘중복 회피 우선, 필요하면 재노출’이며 사용자별 광고 개인화는 없다.
